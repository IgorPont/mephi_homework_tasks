# Анализ сайта "СберАвтоподписка"

## Описание проекта

Проект посвящен анализу пользовательского поведения на сайте сервиса "СберАвтоподписка".

Цель проекта -> построить модель машинного обучения, которая предсказывает вероятность совершения пользователем целевого
действия на сайте.

К целевым действиям относятся:

- успешная отправка заявки
- заявка на автомобиль по подписке
- заказ звонка
- переход к звонку
- открытие диалога или чата
- другие значимые действия, связанные с интересом пользователя к сервису

Результаты модели могут быть использованы для:

- оценки эффективности каналов привлечения трафика
- анализа поведения пользователей на сайте
- выявления признаков, связанных с конверсией
- повышения качества рекламных кампаний
- приоритизации пользователей с высокой вероятностью целевого действия

## Описание данных

В проекте используются данные Google Analytics по сайту "СберАвтоподписка".

Исходные данные представлены двумя логическими таблицами:

- `ga_sessions` -> данные о визитах пользователей
- `ga_hits` -> данные о событиях пользователей внутри визитов

Файлы исходных данных размещаются в директории `data/raw/`:

- `data/raw/ga_sessions.pkl`
- `data/raw/ga_hits.pkl`
- `data/raw/ga_sessions.csv`
- `data/raw/ga_hits.csv`

Основным форматом для работы является `.pkl`, так как он быстрее загружается и лучше сохраняет структуру
`pandas.DataFrame`.
CSV-файлы используются как резервный вариант, если pickle-файлы отсутствуют.

## Таблица `ga_sessions`

Файл `ga_sessions` содержит данные о визитах пользователей на сайт.

Одна строка соответствует одному визиту.

Основные признаки:

- `session_id` -> ID визита
- `client_id` -> ID пользователя
- `visit_date` -> дата визита
- `visit_time` -> время визита
- `visit_number` -> порядковый номер визита пользователя
- `utm_source` -> источник трафика
- `utm_medium` -> тип трафика
- `utm_campaign` -> рекламная кампания
- `utm_adcontent` -> содержание рекламного объявления
- `utm_keyword` -> ключевое слово
- `device_category` -> тип устройства
- `device_os` -> операционная система
- `device_brand` -> бренд устройства
- `device_model` -> модель устройства
- `device_screen_resolution` -> разрешение экрана
- `device_browser` -> браузер
- `geo_country` -> страна
- `geo_city` -> город

## Таблица `ga_hits`

Файл `ga_hits` содержит данные о действиях пользователей на сайте.

Одна строка соответствует одному событию внутри визита.

Основные признаки:

- `session_id` -> ID визита
- `hit_date` -> дата события
- `hit_time` -> время события
- `hit_number` -> порядковый номер события в рамках визита
- `hit_type` -> тип события
- `hit_referer` -> источник события
- `hit_page_path` -> страница события
- `event_category` -> категория события
- `event_action` -> действие пользователя
- `event_label` -> метка события
- `event_value` -> значение события

## Целевая переменная

Целевая переменная формируется на уровне визита.

```text
target = 1 -> если в рамках визита пользователь совершил хотя бы одно целевое действие
```

```text
target = 0 -> если в рамках визита целевого действия не было
```

Целевые действия определяются по полю `ga_hits.event_action`.

Итоговый список целевых действий хранится в файле `src/config.py` в константе `TARGET_ACTIONS`.

```python
TARGET_ACTIONS = [
    "sub_submit_success",
    "sub_car_claim_submit_click",
    "sub_car_request_submit_click",
    "sub_custom_question_submit_click",
    "sub_callback_submit_click",
    "sub_call_number_click",
    "callback requested",
    "form_request_call_sent",
    "click_on_request_call",
    "sub_open_dialog_click",
    "chat requested",
    "chat established",
    "client initiate chat",
    "user gave contacts during chat",
    "start_chat",
    "greenday_sub_submit_success",
    "greenday_sub_callback_submit_click",
    "greenday_sub_call_number_click",
    "greenday_sub_open_dialog_click",
    "request_success",
]
```

По результатам подготовки данных доля целевого класса составила около `3.38%`, поэтому задача является задачей бинарной
классификации с выраженным дисбалансом классов.

## Этапы работы

### 1. Разведочный анализ данных

Основной ноутбук -> `notebooks/01_eda.ipynb`.

На этапе EDA выполнено:

- загружены исходные таблицы `ga_sessions` и `ga_hits`
- изучены размеры таблиц и типы данных
- проверены пропуски
- проверены дубликаты
- изучены категориальные признаки
- проанализированы источники и типы трафика
- изучены пользовательские события `event_action`
- сформирован список целевых действий
- создана целевая переменная `target`
- оценено распределение целевого класса
- построены графики по пропускам, конверсии и распределению `target`

Важные промежуточные выводы:

- в `ga_sessions` больше всего пропусков было в признаках `device_model`, `utm_keyword`, `device_os`, `utm_adcontent`,
  `utm_campaign` и `device_brand`
- в `ga_hits` полностью отсутствовал `event_value`, поэтому этот признак не использовался
- дубликаты на уровне полных строк в `ga_sessions` не обнаружены
- для `ga_hits` анализ дубликатов выполнялся по ключевым полям, так как таблица содержит события и может иметь
  повторяющиеся действия внутри одной сессии
- наиболее массовым типом устройства является `mobile`
- основной объем трафика пришел из России
- целевой класс составил около `3.38%` от всех визитов

Эти признаки были полезны для EDA и бизнес-интерпретации поведения пользователей, но в финальную модель они не включены
из-за риска утечки данных.

## Проверка признаков на утечку данных

На этапе первичного feature engineering были созданы поведенческие признаки на основе таблицы `ga_hits`.

После анализа было выявлено, что использование таких признаков в модели может приводить к `data leakage`.

Причина заключается в том, что целевая переменная `target` также формируется на основе событий из
`ga_hits.event_action`.
Если агрегировать события по всей сессии, модель получает информацию не только о поведении пользователя до целевого
действия, но и о событиях, которые могли произойти после него.

Например, если пользователь сначала отправил заявку, а затем продолжил взаимодействовать с сайтом, то признаки вроде
количества событий, количества уникальных страниц или количества уникальных действий будут учитывать уже
постконверсионное поведение.

В таком случае модель фактически не предсказывает вероятность будущего целевого действия, а распознает уже состоявшуюся
конверсионную сессию по ее следам.

Поэтому в финальной версии проекта было принято решение:

- использовать `ga_hits` только для формирования целевой переменной
- не использовать агрегированные признаки по событиям всей сессии в финальной модели
- обучать модель только на признаках, доступных на момент начала визита: `utm_*`, `device_*`, `geo_*`, дата и время
  визита, номер визита

В коде проекта дополнительно добавлена проверка отсутствия признаков с риском утечки данных перед обучением модели.

```text
Проверка leakage-признаков: признаки с риском утечки не обнаружены.
```

Итоговый датасет после исправления содержит:

```text
(1860042, 24)
```

Это соответствует `23` признакам и целевой переменной `target`.

Основной ноутбук -> `notebooks/03_modeling.ipynb`.

На этапе моделирования выполнено:

- загружен подготовленный датасет без признаков с риском утечки данных
- признаки отделены от целевой переменной
- выполнена проверка отсутствия leakage-признаков
- определены числовые и категориальные признаки
- данные разделены на train/test в пропорции 80/20
- из-за дисбаланса классов использовано стратифицированное разбиение `stratify=y`
- построен общий `sklearn Pipeline` с обработкой пропусков, масштабированием числовых признаков и кодированием

- лучшая модель сохранена в `models/model.pkl`
- предсказания сохранены в `outputs/predictions.csv`
- метрики сохранены в `outputs/metrics.json`

## Метрики качества

Основная метрика качества -> `ROC-AUC`.

Причина выбора ROC-AUC заключается в том, что в данных выраженный дисбаланс классов, поэтому простая `accuracy` может
вводить в заблуждение.

Baseline-модель, которая всегда предсказывает самый частый класс, получила высокую `accuracy`, но ее ROC-AUC равен
`0.5000`. Это означает, что baseline не умеет отделять целевой класс от нецелевого и соответствует случайному
ранжированию.

По условиям задачи необходимо было ориентироваться на `ROC-AUC >= 0.65`.

Итоговая исправленная модель немного превысила этот ориентир.

## Результаты моделирования после исправления

Финальная модель обучалась только на признаках, доступных на момент начала визита.

| Модель             | Accuracy | ROC-AUC |
|--------------------|---------:|--------:|
| DummyClassifier    |   0.9662 |  0.5000 |
| LogisticRegression |   0.5467 |  0.6692 |

Лучшей моделью по ROC-AUC стала `LogisticRegression`.

Итоговые метрики лучшей модели:

```text
Accuracy: 0.5467
ROC-AUC: 0.6692
```

Матрица ошибок для `LogisticRegression`:

```text
[[194761 164668]
 [  3949   8631]]
```

Интерпретация:

- модель правильно нашла `8631` визит с целевым действием
- модель пропустила `3949` целевых визитов
- recall целевого класса составил около `0.69`, то есть модель находит значительную часть потенциально конверсионных
  визитов
- precision целевого класса составил около `0.05`, что связано с сильным дисбалансом классов и использованием
  `class_weight="balanced"`
- для такой задачи модель лучше использовать не как жесткий бинарный классификатор по порогу `0.5`, а как инструмент
  ранжирования визитов по вероятности целевого действия

## Сравнение первой и исправленной версии модели

В первой версии модели использовались как признаки визита, так и агрегированные признаки поведения пользователя внутри
всей сессии.

Первая версия модели показала высокое значение ROC-AUC:

```text
ROC-AUC: 0.9272
```

Однако после анализа признаков было выявлено, что такая оценка является завышенной из-за утечки данных.

Проблемные признаки:

- `hit_count`
- `max_hit_number`
- `unique_page_count`
- `unique_event_action_count`
- `unique_event_category_count`
- `has_view_card`
- `has_search`
- `has_pagination`
- `has_quiz`
- `has_subscription_interest`
- `has_phone_interaction`
- `has_form_interaction`

Эти признаки рассчитывались по полной сессии и могли включать события, произошедшие после целевого действия.

В исправленной версии модели поведенческие признаки из `ga_hits` были исключены из обучающей выборки. Таблица `ga_hits`
используется только для формирования `target`.

Финальная модель обучается на признаках, доступных на момент начала визита:

- источник трафика
- тип трафика
- рекламная кампания
- ключевое слово
- рекламное объявление
- устройство
- браузер
- география
- дата и время визита
- номер визита пользователя

После исправления ROC-AUC снизился с `0.9272` до `0.6692`.
Это ожидаемый результат: модель больше не использует поведение пользователя из будущего.

При этом итоговая модель остается лучше baseline и превышает ориентир задачи `0.65`.
Такой результат является более честным и лучше соответствует прикладному сценарию: предсказать вероятность целевого
действия по данным визита.

### Получение предсказания

Скрипт загружает сохраненную модель и возвращает предсказание целевого действия для одного визита из подготовленного
датасета.

```bash
poetry run python -m sessions_tasks.classical_ml.session02.sber_auto_subscription.src.predict
```

Пример вывода:

```json
{
  "prediction": 1,
  "probability": 0.5133,
  "true_target": 0
}
```

Расшифровка:

```text
prediction = 0 -> модель считает, что целевого действия не будет при текущем пороге
prediction = 1 -> модель считает, что целевое действие будет при текущем пороге
probability -> оценка вероятности целевого действия
true_target -> фактическое значение из датасета, добавлено только для проверки
```

Важно учитывать, что в задаче с сильным дисбалансом классов бинарный прогноз зависит от выбранного порога.
Для практического применения полезнее использовать `probability` для ранжирования визитов по вероятности
целевого действия.

## Итоговый вывод

В ходе проекта был выполнен полный цикл решения задачи бинарной классификации: от разведочного анализа данных и
формирования целевой переменной до генерации признаков, обучения модели, сравнения с baseline и сохранения итогового
pipeline.

На первом этапе была построена модель с использованием признаков визита и поведенческих агрегатов по событиям внутри
всей сессии. Эта версия показала ROC-AUC около `0.9272`, однако последующая проверка выявила риск утечки данных.

Причина заключалась в том, что поведенческие признаки рассчитывались по всей сессии, тогда как целевая переменная также
формировалась на основе событий внутри этой же сессии. Из-за этого модель могла получать информацию о действиях,
произошедших после целевого события.

В исправленной версии проекта `ga_hits` используется только для формирования `target`. Финальная модель обучается на
признаках, доступных на момент начала визита: источниках трафика, устройстве, географии, времени визита и номере визита
пользователя.

Данные имеют выраженный дисбаланс классов: только около `3.38%` визитов содержат целевое действие. Поэтому в качестве
основной метрики была выбрана ROC-AUC, а baseline-модель использовалась как контрольная точка.

Baseline-модель `DummyClassifier` показала ROC-AUC `0.5000`.
Итоговая модель `LogisticRegression` показала ROC-AUC `0.6692`, что выше baseline и выше ориентира задачи `0.65`.

Результат исправленной модели ниже, чем в первой версии, но является более честным, так как модель больше не использует
информацию о будущих действиях пользователя.

Модель может использоваться для оценки вероятности целевого действия и ранжирования визитов по степени потенциальной
конверсии.
