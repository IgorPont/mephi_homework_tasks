# Анализ сайта "СберАвтоподписка"

## Описание проекта

Проект посвящен анализу пользовательского поведения на сайте сервиса "СберАвтоподписка".

Цель проекта -> построить модель машинного обучения, которая предсказывает вероятность совершения пользователем целевого
действия на сайте.

К целевым действиям относятся:

- успешная отправка заявки
- заявка на автомобиль по подписке
- заказ звонка
- переход к звонку
- открытие диалога или чата
- другие значимые действия, связанные с интересом пользователя к сервису

Результаты модели могут быть использованы для:

- оценки эффективности каналов привлечения трафика
- анализа поведения пользователей на сайте
- выявления признаков, связанных с конверсией
- повышения качества рекламных кампаний
- приоритизации пользователей с высокой вероятностью целевого действия

## Описание данных

В проекте используются данные Google Analytics по сайту "СберАвтоподписка".

Исходные данные представлены двумя логическими таблицами:

- `ga_sessions` -> данные о визитах пользователей
- `ga_hits` -> данные о событиях пользователей внутри визитов

Файлы исходных данных размещаются в директории `data/raw/`:

- `data/raw/ga_sessions.pkl`
- `data/raw/ga_hits.pkl`
- `data/raw/ga_sessions.csv`
- `data/raw/ga_hits.csv`

Основным форматом для работы является `.pkl`, так как он быстрее загружается и лучше сохраняет структуру
`pandas.DataFrame`.
CSV-файлы используются как резервный вариант, если pickle-файлы отсутствуют.

## Таблица `ga_sessions`

Файл `ga_sessions` содержит данные о визитах пользователей на сайт.

Одна строка соответствует одному визиту.

Основные признаки:

- `session_id` -> ID визита
- `client_id` -> ID пользователя
- `visit_date` -> дата визита
- `visit_time` -> время визита
- `visit_number` -> порядковый номер визита пользователя
- `utm_source` -> источник трафика
- `utm_medium` -> тип трафика
- `utm_campaign` -> рекламная кампания
- `utm_keyword` -> ключевое слово
- `device_category` -> тип устройства
- `device_os` -> операционная система
- `device_brand` -> бренд устройства
- `device_model` -> модель устройства
- `device_screen_resolution` -> разрешение экрана
- `device_browser` -> браузер
- `geo_country` -> страна
- `geo_city` -> город

## Таблица `ga_hits`

Файл `ga_hits` содержит данные о действиях пользователей на сайте.

Одна строка соответствует одному событию внутри визита.

Основные признаки:

- `session_id` -> ID визита
- `hit_date` -> дата события
- `hit_time` -> время события
- `hit_number` -> порядковый номер события в рамках визита
- `hit_type` -> тип события
- `hit_referer` -> источник события
- `hit_page_path` -> страница события
- `event_category` -> категория события
- `event_action` -> действие пользователя
- `event_label` -> метка события
- `event_value` -> значение события

## Целевая переменная

Целевая переменная формируется на уровне визита.

```text
target = 1 -> если в рамках визита пользователь совершил хотя бы одно целевое действие
```

```text
target = 0 -> если в рамках визита целевого действия не было
```

Целевые действия определяются по полю `ga_hits.event_action`.

Итоговый список целевых действий хранится в файле `src/config.py` в константе `TARGET_ACTIONS`.

В итоговой версии проекта используются следующие целевые действия:

```python
TARGET_ACTIONS = [

    "sub_car_request_submit_click",
    "sub_custom_question_submit_click",
```

классификации с выраженным дисбалансом классов.

## Этапы работы

### 1. Разведочный анализ данных

Основной ноутбук -> `notebooks/01_eda.ipynb`

На этапе EDA выполнено:

- загружены исходные таблицы `ga_sessions` и `ga_hits`
- изучены размеры таблиц и типы данных
- проверены пропуски
- проверены дубликаты
- изучены категориальные признаки
- проанализированы источники и типы трафика
- изучены пользовательские события `event_action`
- сформирован список целевых действий
- создана целевая переменная `target`
- оценено распределение целевого класса
- построены графики по пропускам, конверсии и распределению target

Важные промежуточные выводы:

- в `ga_sessions` больше всего пропусков было в признаках `device_model`, `utm_keyword`, `device_os`, `utm_adcontent`,
  `utm_campaign` и `device_brand`
- в `ga_hits` полностью отсутствовал `event_value`, поэтому этот признак не использовался
- дубликаты на уровне полных строк в `ga_sessions` не обнаружены
- для `ga_hits` анализ дубликатов выполнялся по ключевым полям, так как таблица содержит события и может иметь
  повторяющиеся действия внутри одной сессии
- наиболее массовым типом устройства является `mobile`
- основной объем трафика пришел из России
- целевой класс составил около `3.38%` от всех визитов

### 2. Feature Engineering

Основной ноутбук -> `notebooks/02_feature_engineering.ipynb`

На этом этапе были созданы дополнительные признаки для модели.

Признаки на основе визитов:

- `visit_month` -> месяц визита
- `visit_day` -> день месяца
- `visit_weekday` -> день недели
- `visit_hour` -> час визита
- `is_weekend` -> признак выходного дня
- `is_organic_traffic` -> признак органического трафика
- `is_paid_traffic` -> признак платного трафика
- `is_social_traffic` -> признак трафика из социальных источников
- `is_first_visit` -> признак первого визита пользователя
- `visit_number_clipped` -> ограниченная версия номера визита

Агрегированные признаки из событий:

- `hit_count` -> количество событий в визите
- `max_hit_number` -> максимальный номер события
- `unique_page_count` -> количество уникальных страниц
- `unique_event_action_count` -> количество уникальных действий
- `unique_event_category_count` -> количество уникальных категорий событий

Бинарные поведенческие признаки:

- `has_view_card` -> пользователь просматривал карточку автомобиля
- `has_search` -> пользователь взаимодействовал с поиском
- `has_pagination` -> пользователь использовал пагинацию
- `has_quiz` -> пользователь видел или запускал квиз
- `has_subscription_interest` -> пользователь проявлял интерес к подписке
- `has_phone_interaction` -> пользователь взаимодействовал с телефонными действиями
- `has_form_interaction` -> пользователь взаимодействовал с формами

### 3. Обучение моделей

Основной ноутбук -> `notebooks/03_modeling.ipynb`

На этапе моделирования выполнено:

- загружен подготовленный датасет
- признаки отделены от целевой переменной
- определены числовые и категориальные признаки
- данные разделены на train/test в пропорции 80/20
- из-за дисбаланса классов использовано стратифицированное разбиение `stratify=y`
- построен общий `sklearn Pipeline` с обработкой пропусков, масштабированием числовых признаков и кодированием
  категориальных признаков
- обучена baseline-модель `DummyClassifier`
- обучена модель `LogisticRegression`
- дополнительно проверена модель `RandomForestClassifier`
- модели сравнены по ROC-AUC
- лучшая модель сохранена в `models/model.pkl`
- предсказания сохранены в `outputs/predictions.csv`
- метрики сохранены в `outputs/metrics.json`

## Метрики качества

Основная метрика качества -> `ROC-AUC`

Причина выбора ROC-AUC заключается в том, что в данных выраженный дисбаланс классов, поэтому простая accuracy
может вводить в заблуждение.
По результатам обучения установлено, что baseline-модель, которая всегда предсказывает самый частый класс,
получила accuracy около `0.9662`, но ее ROC-AUC равен `0.5000`, то есть она не умеет отделять
целевой класс от нецелевого.

По условиям задачи необходимо было оринтерироваться на `ROC-AUC >= 0.65`

Итоговая обученная модель существенно превысила этот ориентир.

## Результаты моделирования

| Модель                 | Accuracy | ROC-AUC |
|------------------------|----------|---------|
| DummyClassifier        | 0.9662   | 0.5000  |
| LogisticRegression     | 0.8700   | 0.9272  |
| RandomForestClassifier | 0.7156   | 0.8739  |

Лучшей моделью по ROC-AUC установлена `LogisticRegression`.

Итоговые метрики лучшей модели:

```text
Accuracy: 0.8700
ROC-AUC: 0.9272
```

Матрица ошибок для `LogisticRegression`:

```text
[[313399  46030]
 [  2342  10238]]
```

Интерпретация:

- модель правильно нашла `10238` визитов с целевым действием
- модель пропустила `2342` целевых визита
- recall целевого класса составил около `0.81`, то есть модель находит большую часть потенциально конверсионных визитов
- precision целевого класса составил около `0.18`, что ожидаемо при сильном дисбалансе классов и ориентации на поиск
  целевых пользователей

## Итоговый вывод

В ходе проекта был выполнен полный цикл решения задачи бинарной классификации, от разведочного анализа данных и
формирования целевой переменной до генерации признаков, обучения моделей, сравнения качества и сохранения итогового
pipeline.

Данные имеют выраженный дисбаланс классов, только около `3.38%` визитов содержат целевое действие. Поэтому в качестве
основной метрики была выбрана ROC-AUC, а baseline-модель использовалась только как контрольная точка.

Лучшая модель -> `LogisticRegression`.
Она показала ROC-AUC около `0.9272`, что существенно выше baseline ROC-AUC `0.5000` и выше требуемого ориентира `0.65`.

Модель хорошо ранжирует визиты по вероятности совершения целевого действия и может использоваться для оценки
потенциально конверсионных пользователей, анализа каналов трафика и дальнейшей оптимизации сайта.
