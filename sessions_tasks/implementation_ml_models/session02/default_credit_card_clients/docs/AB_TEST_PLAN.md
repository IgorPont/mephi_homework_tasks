# План A/B-тестирования ML-модели

## 1. Цель A/B-теста

Цель A/B-тестирования -> проверить, улучшает ли новая модель прогнозирования дефолта качество кредитного скоринга по
сравнению с базовой моделью.

В проекте сравниваются две версии модели:

- `v1` -> базовая модель `LogisticRegression`
- `v2` -> новая модель `RandomForestClassifier`

По результатам offline-оценки модель `v2` показала более высокие значения `F1-score` и `ROC-AUC`, поэтому она выбрана
основной моделью для API. Однако перед промышленным внедрением необходимо проверить ее влияние на бизнес-метрики.

## 2. Гипотеза

Новая модель `v2` позволит точнее выявлять клиентов с высоким риском дефолта и снизит финансовые потери кредитной
организации без чрезмерного увеличения отказов добросовестным клиентам.

Формально:

- нулевая гипотеза `H0` -> модель `v2` не улучшает бизнес-результаты по сравнению с `v1`
- альтернативная гипотеза `H1` -> модель `v2` улучшает бизнес-результаты по сравнению с `v1`

## 3. Описание моделей

### Модель A -> контрольная группа

Версия модели -> `v1`

Алгоритм -> `LogisticRegression`

Метрики на тестовой выборке:

| Метрика   | Значение |
|-----------|---------:|
| Accuracy  |   0.6797 |
| Precision |   0.3672 |
| Recall    |   0.6202 |

### Модель B -> тестовая группа

Метрики на тестовой выборке:

| Метрика   | Значение |
|-----------|---------:|
| Accuracy  |   0.7872 |

## 4. Разделение трафика

Для проведения A/B-теста входящие запросы можно разделить на две группы:

| Группа | Доля трафика | Версия модели | Описание              |
|--------|-------------:|---------------|-----------------------|
| A      |          50% | `v1`          | Контрольная модель    |
| B      |          50% | `v2`          | Новая модель-кандидат |

В рамках учебного проекта для демонстрации реализованы отдельные эндпоинты:

```text
POST /predict/v1
POST /predict/v2
```

В промышленной версии распределение трафика может выполняться автоматически на уровне API Gateway, балансировщика,
backend-сервиса или отдельного A/B testing-сервиса.

## 5. Принцип назначения пользователя в группу

Для корректного эксперимента клиент должен попадать в одну и ту же группу на протяжении всего теста.

Возможный способ назначения:

```text
hash(client_id) % 100 < 50  -> группа A
hash(client_id) % 100 >= 50 -> группа B
```

Такой подход обеспечивает:

- стабильное попадание клиента в группу
- равномерное распределение трафика
- отсутствие ручного выбора модели оператором
- воспроизводимость результатов эксперимента

## 6. Основные ML-метрики

На этапе тестирования необходимо отслеживать следующие ML-метрики:

| Метрика          | Смысл                                                                           |
|------------------|---------------------------------------------------------------------------------|
| Precision        | Доля реально дефолтных клиентов среди тех, кого модель отметила как рискованных |
| Recall           | Доля найденных дефолтных клиентов среди всех фактических дефолтов               |
| F1-score         | Баланс между precision и recall                                                 |
| ROC-AUC          | Способность модели разделять клиентов по уровню риска                           |
| Confusion Matrix | Количество TP, FP, TN, FN                                                       |

Особое внимание следует уделять ошибкам двух типов:

- `False Positive` -> модель ошибочно считает хорошего клиента рискованным
- `False Negative` -> модель ошибочно считает рискованного клиента хорошим

Для кредитного скоринга ошибка `False Negative` обычно опаснее, так как она может привести к выдаче кредита клиенту,
который уйдет в дефолт.

## 7. Основные бизнес-метрики

Для принятия решения о внедрении модели нужно оценивать не только ML-метрики, но и бизнес-показатели.

| Метрика                | Описание                                      |
|------------------------|-----------------------------------------------|
| Default Rate           | Доля дефолтов среди одобренных клиентов       |
| Approval Rate          | Доля одобренных заявок                        |
| Bad Rate               | Доля проблемных клиентов в портфеле           |
| Profit per Application | Средняя прибыль на одну заявку                |
| Loss Rate              | Финансовые потери от дефолтов                 |
| Revenue                | Доход от одобренных клиентов                  |
| Missed Revenue         | Упущенный доход из-за отказа хорошим клиентам |

Главная бизнес-цель -> снизить потери от дефолтов, не допустив чрезмерного падения количества качественных одобренных
клиентов.

## 8. Логирование эксперимента

Для каждого запроса необходимо логировать:

- уникальный идентификатор клиента или заявки
- версию модели
- входные признаки
- прогноз модели
- вероятность дефолта
- итоговое бизнес-решение
- дату и время запроса
- фактический результат после наступления периода наблюдения

Пример логируемой записи:

```json
{
  "request_id": "abc-123",
  "client_id": "client-001",
  "model_version": "v2",
  "prediction": 1,
  "probability": 0.827695,
  "decision": "reject_or_manual_review",
  "timestamp": "2026-06-06T14:43:56Z"
}
```

Фактический дефолт станет известен позже, поэтому финальная оценка модели выполняется после накопления достаточного
количества наблюдений.

## 9. Продолжительность теста

Рекомендуемая продолжительность A/B-теста зависит от объема заявок и скорости накопления фактических дефолтов.

Для учебного проекта можно описать следующий план:

- минимальная длительность теста -> 4 недели
- рекомендуемая длительность -> 1–3 месяца
- финальная оценка -> после появления фактических данных по дефолтам за следующий месяц

Тест нельзя завершать только по первым результатам, так как поведение клиентов и качество портфеля могут меняться по
дням и неделям.

## 10. Критерии успешности

Модель `v2` можно считать успешной, если выполняются условия:

1. `ROC-AUC` и `F1-score` не ниже, чем у `v1`
2. Доля дефолтов среди одобренных клиентов снижается
3. Финансовые потери от дефолтов снижаются
4. Доля отказов хорошим клиентам не растет критически
5. Средняя прибыль на заявку увеличивается или не ухудшается
6. Время ответа API остается приемлемым
7. Количество технических ошибок сервиса не увеличивается

## 11. Guardrail-метрики

Помимо целевых метрик, нужно контролировать ограничивающие метрики.

| Guardrail-метрика                 | Почему важна                                    |
|-----------------------------------|-------------------------------------------------|
| Среднее время ответа API          | Модель не должна замедлять клиентский путь      |
| Доля ошибок 5xx                   | Сервис должен оставаться стабильным             |
| Доля отказов                      | Модель не должна резко сокращать выдачи         |
| Доля ручных проверок              | Нельзя перегрузить сотрудников ручным скорингом |
| Распределение клиентов по группам | Группы A и B должны быть сопоставимы            |

Если guardrail-метрики ухудшаются, тест нужно остановить или пересмотреть параметры модели.

## 12. Возможные решения по итогам теста

По итогам A/B-теста возможны следующие решения:

### Вариант 1. Полное внедрение модели v2

Используется, если модель `v2` улучшила ML-метрики и бизнес-метрики без ухудшения guardrail-метрик.

### Вариант 2. Частичное внедрение

Используется, если модель `v2` хорошо работает только на части клиентов, например:

- на клиентах с определенным кредитным лимитом
- на новых клиентах
- на клиентах с высоким уровнем задолженности
- на отдельных продуктовых сегментах

### Вариант 3. Возврат к модели v1

Используется, если модель `v2` не дала значимого улучшения или ухудшила бизнес-показатели.

### Вариант 4. Доработка модели

Используется, если модель показала потенциал, но требует:

- настройки порога классификации
- добавления новых признаков
- переобучения на новых данных
- более точной калибровки вероятностей
- дополнительной проверки fairness-метрик

## 13. Риски A/B-тестирования

Основные риски:

- группы A и B могут оказаться несбалансированными
- фактический дефолт становится известен не сразу
- бизнес-процесс может измениться во время эксперимента
- операторы могут по-разному обрабатывать заявки из разных групп
- модель может давать перекос по отдельным группам клиентов
- качество данных может измениться после запуска

Для снижения рисков необходимо фиксировать правила эксперимента заранее и не менять их в процессе тестирования без
отдельного решения.

## 14. Итоговый вывод

A/B-тестирование позволяет проверить не только offline-качество модели, но и ее реальное влияние на бизнес.

В данном проекте модель `v2` показывает лучшие offline-метрики, поэтому она выбрана кандидатом на внедрение. Однако
окончательное решение о переходе на `v2` должно приниматься после анализа фактических бизнес-результатов:

- уровня дефолтов
- доли одобрений
- финансовых потерь
- прибыли на заявку
