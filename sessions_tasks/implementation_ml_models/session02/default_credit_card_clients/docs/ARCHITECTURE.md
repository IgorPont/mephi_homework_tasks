# Архитектура сервиса прогнозирования дефолта

## 1. Назначение сервиса

Сервис предназначен для прогнозирования вероятности дефолта клиента по кредитной карте на следующий месяц.

На вход сервис получает финансовые и поведенческие признаки клиента, после чего возвращает:

- прогноз класса:
    - `0` -> дефолт не ожидается
    - `1` -> ожидается дефолт
- вероятность дефолта
- версию использованной модели
- текстовую метку риска

## 2. Общая схема решения

Проект реализован как монолитный ML API-сервис.

```text
Клиент / внешняя система
        |
        v
Flask API + Gunicorn
        |
        v
ModelHandler
        |
        v
Загруженная ML-модель joblib
        |
        v
JSON-ответ с прогнозом
```

## 3. Выбранный архитектурный подход

Для учебного проекта выбран монолитный подход.

В одном сервисе объединены:

- REST API
- валидация входных данных
- загрузка модели
- выполнение инференса
- формирование ответа
- логирование событий

Такой подход выбран потому, что задача имеет небольшой объем, не требует сложной распределенной обработки и хорошо
укладывается в один контейнер.

## 4. Почему не микросервисная архитектура

Микросервисная архитектура была бы оправдана, если бы система включала:

- отдельный сервис авторизации
- отдельный сервис фичей
- отдельный сервис хранения заявок
- отдельный сервис мониторинга
- отдельный сервис переобучения модели
- несколько ML-моделей с независимым жизненным циклом

В текущем проекте это избыточно.
Монолитный ML API проще развернуть, протестировать и сопровождать.

## 5. Компоненты проекта

### Flask API

Файл:

```text
app/api.py
```

Отвечает за HTTP-интерфейс сервиса.

Реализованы эндпоинты:

- `GET /health` -> проверка работоспособности сервиса
- `POST /predict` -> прогноз моделью по умолчанию
- `POST /predict/v1` -> прогноз моделью v1
- `POST /predict/v2` -> прогноз моделью v2

### ModelHandler

Файл:

```text
app/model_handler.py
```

Отвечает за:

- загрузку моделей из файлов `.joblib`
- выбор версии модели
- выполнение предсказания
- возврат результата в едином формате

### Schemas

Файл:

```text
app/schemas.py
```

Отвечает за:

- список ожидаемых признаков
- проверку входного JSON
- приведение значений к числовому типу
- возврат ошибки при отсутствии обязательных признаков

### Config

Файл:

```text
app/config.py
```

Содержит:

- пути к моделям
- версию модели по умолчанию
- настройки порта и хоста

### Train model

Файл:

```text
models/train_model.py
```

Отвечает за:

- загрузку датасета
- разделение данных на train/test
- обучение моделей
- расчет метрик
- сохранение моделей в формате `joblib`

## 6. Модели

В проекте обучены две модели.

### v1 -> LogisticRegression

Базовая модель для сравнения.

Метрики на тестовой выборке:

| Метрика   | Значение |
|-----------|---------:|
| Accuracy  |   0.6797 |
| Precision |   0.3672 |
| Recall    |   0.6202 |
| F1-score  |   0.4613 |
| ROC-AUC   |   0.7081 |

### v2 -> RandomForestClassifier

Основная модель сервиса.

Метрики на тестовой выборке:

| Метрика   | Значение |
|-----------|---------:|
| Accuracy  |   0.7872 |
| Precision |   0.5168 |
| Recall    |   0.5795 |
| F1-score  |   0.5464 |
| ROC-AUC   |   0.7750 |

Модель `v2` выбрана основной, так как она показывает более высокие значения `F1-score` и `ROC-AUC`.

## 7. Production-запуск

Для локальной разработки можно использовать встроенный Flask-сервер.

Для контейнерного запуска используется Gunicorn:

```text
gunicorn --bind 0.0.0.0:5001 app.api:app
```

Gunicorn является WSGI-сервером и лучше подходит для production-like запуска Flask-приложения, чем встроенный сервер
Flask.

## 8. Использование NGINX и uWSGI/Gunicorn

В production-среде перед приложением можно разместить NGINX.

NGINX может выполнять следующие функции:

- принимать внешние HTTP/HTTPS-запросы
- завершать TLS-соединения
- проксировать запросы к Gunicorn
- ограничивать размер запросов
- выполнять базовую балансировку нагрузки
- отдавать статические файлы, если они появятся

Пример production-схемы:

```text
Пользователь / внешняя система
        |
        v
      NGINX
        |
        v
     Gunicorn
        |
        v
     Flask API
        |
        v
     ML-модель
```

В этом проекте для простоты используется Gunicorn без отдельного NGINX-контейнера.

## 9. Возможное использование ONNX-ML

В текущем проекте модели сохраняются через `joblib`.

Для production-сценариев модель можно дополнительно конвертировать в формат ONNX.

Преимущества ONNX:

- единый формат хранения моделей
- независимость от конкретной версии scikit-learn
- возможность более быстрого инференса
- удобство переноса модели между разными платформами

Потенциальная схема:

```text
sklearn Pipeline
        |
        v
    ONNX model
        |
        v
   ONNX Runtime
        |
        v
  Prediction API
```

Для учебного проекта `joblib` достаточно, но ONNX может быть полезен при промышленном внедрении.

## 10. Возможное использование RabbitMQ

RabbitMQ может быть полезен, если прогнозирование нужно выполнять асинхронно.

Например:

```text
CRM / банковская система
        |
        v
     RabbitMQ
        |
        v
     ML worker
        |
        v
   База данных с 
результатами скоринга
```

Такой подход уместен, если:

- заявок много
- ответ не требуется мгновенно
- нужно гарантированно обработать каждую заявку
- требуется повторная обработка при ошибках

В текущем проекте используется синхронный REST API, потому что запросы небольшие, а модель отвечает быстро.

## 11. Логирование и мониторинг

В сервисе настроено базовое логирование.

Логируются:

- успешные предсказания
- версия модели
- прогноз
- вероятность дефолта
- ошибки валидации
- внутренние ошибки сервиса

В production можно расширить мониторинг:

- количество запросов
- среднее время ответа
- доля ошибок 4xx и 5xx
- распределение вероятностей дефолта
- доля клиентов, отнесенных к рисковым
- drift признаков
- drift предсказаний
- качество модели после появления фактических дефолтов

Возможные инструменты:

- Prometheus
- Grafana
- ELK / OpenSearch
- Loki
- MLflow
- Evidently AI

## 12. DVC и MLflow

### DVC

DVC можно использовать для версионирования:

- датасетов
- обучающих выборок
- тестовых выборок
- артефактов моделей

Это позволит воспроизводить обучение модели на конкретной версии данных.

### MLflow

MLflow можно использовать для:

- хранения параметров экспериментов
- хранения метрик
- сравнения моделей
- регистрации production-модели
- контроля жизненного цикла моделей

Возможный процесс:

```text
         Данные
           |
           v
     Обучение модели
           |
           v
Логирование метрик в MLflow
           |
           v
Регистрация лучшей модели
           |
           v
   Выкладка модели в API
```

## 13. Бизнес-метрики

Для задачи кредитного скоринга важны не только ML-метрики, но и бизнес-метрики.

Можно отслеживать:

- уровень дефолтов среди одобренных клиентов
- долю отказов по заявкам
- финансовые потери от дефолтов
- упущенную прибыль из-за отказа хорошим клиентам
- средний доход на одного одобренного клиента
- approval rate
- default rate
- profit per approved application

Модель должна снижать финансовые потери, но не должна чрезмерно увеличивать количество отказов добросовестным клиентам.

## 14. Итог

Решение представляет собой контейнеризированный ML API-сервис для прогнозирования дефолта по кредитным картам.

Проект закрывает основные этапы внедрения модели:

- обучение модели
- сохранение артефакта
- загрузка модели
- REST API для инференса
- Docker-контейнеризация
- тестирование
- логирование
- описание production-архитектуры
- подготовка к A/B-тестированию
